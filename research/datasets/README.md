# Datasets

**Updated status:** the `datasets` /
`dataset_versions` tables are no longer empty. A real
`POST /api/v1/datasets` + `POST /api/v1/datasets/{id}/versions` API exists
(`app/api/v1/datasets.py`), and every dataset actually used by a named
experiment script now self-registers a real, checksummed `DatasetVersion`
row and passes its id through `ExperimentConfig.dataset_id` /
`dataset_version_id` before executing - see
`scripts/_pipeline.py::ensure_dataset_registered`. This is why the
`reproducibility_limitation` finding (Section 41) no longer appears on
Experiment 5 (`research/ai/experiment_5_model_comparison.json`) or
Experiment 6 (`research/cybersecurity/experiment_6_ids_comparison.json`)
runs generated after this change - confirmed by re-running both scripts.

## How to (re-)register

```
cd backend
python -m scripts.register_datasets       # synthetic_classification, digits
python -m scripts.run_research_pipeline   # self-registers breast_cancer, then runs Experiment 5
python -m scripts.run_cyber_experiment    # self-registers synthetic_traffic_v1, then runs Experiment 6
```

All three are idempotent (`ensure_dataset_registered` looks up by
`(name)` / `(dataset_id, version_tag)` before inserting), so re-running
them does not create duplicate rows.

## Remaining honest limitation

Quantum (`Domain.QUANTUM`) and PQC (`Domain.PQC`) experiments do not use a
`Dataset` row at all - there is no dataset in the conventional sense for a
quantum circuit simulation or a cryptographic signing-latency benchmark, so
those experiments still correctly show a `reproducibility_limitation`
finding (no dataset_version_id applies) alongside their own environment
metadata (Qiskit/Aer version, `cryptography` library version) which is not
yet independently pinned/recorded anywhere. That is a real, still-open gap,
tracked as a possible future addition (a lightweight "software environment
version" registry, separate from the dataset registry) rather than a
misuse of the dataset model to paper over it.
